## 1. LRC 解析与实测起音校正

### 1.1 LRC 三类行（`80_pv_shotlist.mjs` → `parseLrc`）

| 类 | 判据 | 去向 |
|---|---|---|
| 元信息 | `^\[([a-z]+):(.*)\]$`（`[ti:]`/`[ar:]`） | 丢弃（只留 `meta`） |
| **曲目信息行** | `^[^：]{1,6}：`（**全角冒号**短前缀）或 `^[^—\-]{1,20}\s*[-–—]\s*\S`（"歌名 - 演唱者"） | `lrc.credits` → 片头卡时间轴 |
| 歌词行 | 从第一条非 credit 起，全部 | `lrc.lyrics` |

本歌：**7 行曲目信息**（0 / 4.36 / 8.72 / 13.08 / 17.44 / 21.81 / 26.17s）+ **24 句歌词**（首句 30.53s）。
每句 `nominalEnd` = 下一句的 `t`（末句 `null`，由音频总长兜底）。
**那 7 行的时间码正好铺满 0–30.53s 前奏**——片头三屏卡的排布就是按它来的（见 §6.4）。

### 1.2 包络口径（起音与静音谷的唯一依据）

- 输入是**人声轨** `09_aceproject/初调/翻填.Vocals.wav`，**不是全轨**（全轨有伴奏，能量永不回落，静音谷判不出来）。
- 提取：`ffmpeg -v error -i <wav> -ac 1 -ar 8000 -f s16le -`，即 **8kHz 单声道**、**帧长 20ms**（8000Hz × 0.02 = 160 采样/帧），逐帧 RMS → dBFS。
- **分位只在 `> −90 dBFS` 的活跃帧上取**——否则尾部数字静音会把噪声底拉到 −160，分位数全废。
- 平滑：**±5 帧 = ±100ms** 滑动均值（`sm[]`）；起音与静音谷**都跑在 `sm` 上**。
- 本歌 envelope 分位（dBFS）：p10 **−50.06** / p25 **−34.99** / p50 **−24.95** / p75 −23.09 / p90 **−21.47** / p97 −20.32。

读这些数的正确姿势：**p90 ≈ −21.5** 是"唱歌时的典型峰值"，低于它的基本是非歌唱帧；**p25 ≈ −35** 是"低能量但非静音"的界线，真静音谷远低于它（本歌 73 dB）。

**起音（onset）**：在 `[t−0.8, t+0.8]` 内找 `sm[i] − sm[i−4]`（**80ms 差分**）的最大正值帧 = "最陡能量上升点"；`dev = onset − t`。
**收声（sungEnd）**：从 onset 起累计峰值 `peak`；当 `t > onset + 0.35` 且 `levelIn(t±0.15) ≤ peak − 12dB` 判定唱完，搜索上限 `onset + 12s`。

> ⚠️ **连续句会被"串起来"**：本歌第 4/5/6 句连唱，三句的 `vocalEnd` 都是 **56.16**；11/12/13 → 90.64；20/21/22 → 146.24；23/24 → 152.34。
> 所以 `vocalEnd` **不是逐句精确值**，而是"该句之后第一次能量回落"。这也解释了第 6 句的 −0.78s：它的 `onset` 53.42 **落在第 5 句的发声区间内**，是第 5 句能量尾巴的误检（连唱时 VAD 切不开）。反推校验法：看这句与**前一句 `vocalEnd`** 之间有没有 ≥0.3s 的谷。

### 1.4 为什么必须以实测起音为准

1. **LRC 是词格，不是录音时刻。** 它是按小节写给人看的对齐表；演唱抢拍/拖拍、ACE 渲染的辅音起音都不受词格约束。
2. **偏差的量级是看得见的。** 0.78s / 0.81s ≈ **19 帧 @24fps**——字幕晚了近一秒，观众会明确感到"字跟不上声"。
3. **第 24 句的偏差正好压在段边界上。** 第 24 句 LRC 149.17 **恰好等于段 16 的起点**（149.17），而实测起音在 149.98。若按 LRC 走，字幕会先出现、画面才切进来。
4. **但也不能全信 onset。** 检测的是"最陡上升"，气声、换气、串音都可能伪造一个上升点；第 6 句就是实例。故只对超阈值句动手，且**单句封顶**：

```
|dev| ≤ 0.35s  →  用 LRC 原值（人工标注更稳）
|dev| > 0.35s  →  use = t + clamp(dev, −0.6, +0.6)
```

## 2. 边界吸附

### 2.1 为什么要吸附

段与段是 **concat 硬切直拼**（见 §7）。切点落在有声区 = 半截音节被斩断；落在歌词句内部 = 一句词跨两段画面。所以切点必须落在**静音谷**里。

### 2.2 判定口径

| 判定 | 条件 |
|---|---|
| 纯静音区（直接放行） | `levelIn(t−1.5, t+1.5) < −70 dB` |
| 静音谷（≥8 dB 即可） | `gapScore(t) = levelIn(t−2, t+2) − levelIn(t−0.25, t+0.25) ≥ 8 dB` |
| 落在歌词里（禁止） | `t > onset + 0.05 && t < vocalEnd − 0.05` |
| 正好是句首（最理想） | `t` 命中某个 `lyricStarts` → **直接跳过检查** |

> **判据顺序很重要**：先看是不是某句的起点，再看是不是落在**别的**句的 `[onset, vocalEnd]` 区间内。否则本歌第 4/5/6 句连唱（第 4 句的 `vocalEnd` = 56.16 罩住了 54.2）会把 54.2 这个合法切点误报成"切断歌词"。

### 2.3 吸附算法

对每个**非句首**的原定切点：在 **±2.5s** 内以 **0.02s** 步长扫描；跳过落在任何歌词发声区间内的候选点；要求离前后邻点各 **≥4s**；取 score 最大者（纯静音区记 `1e6`，否则用 `gapScore`）。最优解仍不达标则**不移动**，并在报告里报 problem。

### 2.4 本歌实测

```
157.0s → 159.5s（移动 +2.5s，静音余量 73.195 dB）
```

- 原定尾奏切点 157.0s 落在有声区，被吸到 **159.5s**——**正好撞上 ±2.5s 扫描上限**，说明 159.5s 是右方向的极值。人声到 159.5s 才真正收声（末句 `sungEnd` 只到 152.34，其后仍有尾音/混响拖尾）。
- 连带结果：段 16 = `149.17–159.5`（10.33s / 生成 11s），段 17 = `159.5–165.86`（6.36s / 生成 7s）。
- **全片只有这 1 处吸附**；其余 16 个切点本来就落在句首或静音谷里（句首直接跳过检查）。

**"真实停顿"的四条判据**：① 切点在**所有** `[onset, vocalEnd]` 之外（`insideAnyLyric(t) === false`）；② `gapScore ≥ 8 dB`（本歌实测 73.195 dB，量级远超门槛）；③ 两侧段长各 **≥4s**；④ 目视 `alignment_report.md` 的吸附段（脚本把 `from / to / delta / score` 全写出来，**不靠记忆**）。

`problems[]` 的四类硬校验：段间首尾相接（±1e−6）；末段 `end == 音频总长`（±1e−3）；每段 `dur ≤ 15.0001s` 且 `genDur ∈ [4,15]`；边界不得落在任一句的 `(onset+0.05, vocalEnd−0.05)` 内。非空则 `80` 会 `exitCode = 1`（**不静默通过**）。

## 4. 参考图准备（`scripts/81_pv_refs.mjs`）

源 `01_input/CG/` → 产物 `10_h3video/pv/refs/ref_<原名去扩展名>.jpg`。本歌 **11 张**。

**为什么必须去水印**：H3 的 `reference_image` 会**强影响**生成结果（照着参考图重建画面）；多数官方 CG 带「崩坏3 / HONKAI IMPACT」logo 或年份文字，直接送进去**会把水印画进成片**。

### 4.1 去水印：`delogo`，位置要**逐图声明**，不能一律左上

| 位置码 | 参数（按 `ffprobe` 实测尺寸的百分比算） |
|---|---|
| `tl` 左上 | `delogo=x=0.005W:y=0.008H:w=0.145W:h=0.105H` |
| `br` 右下 | `w=0.30W:h=0.10H`；`x=W−w−0.004W`；`y=H−h−0.008H` |
| `false` 无水印 | 不加滤镜 |

- **水印可能在左下/右下，不总是左上**：本歌 `10th.jpg`、`ElysianRealm.png` 走 **`br`**；`屏幕截图(321/115/163)`、`月下1`、`月下3` 无需处理；`德丽莎2022生日`、`星海绘卷`、`然后向着明天`、`薪火传承` 走 `tl`。
- **右下那块比左上大得多**（宽 30% vs 14.5%）：右下常见"平台水印 + 落款"组合，别照抄 `tl` 的尺寸。
- 判定水印位置的办法：**先看图**（`image_vision`）。`delogo` 只在**确实有水印**时加——它在画面上留的是一块模糊补丁，宁愿裁掉也不要乱擦。
- **尺寸必须用 `ffprobe -select_streams v:0 -show_entries stream=width,height -of csv=p=0` 取**，不要解析 ffmpeg stderr（会匹配到无关数字，脚本注释里专门写了这条）。

### 4.2 缩放与比例

- 统一表达式：`scale='min(1536,iw)':-2:flags=lanczos` —— **只缩不放**，宽 ≤1536、高为偶数；输出 `-q:v 3 -pix_fmt rgb24`。
- **`81` 不做比例归一，也不做裁剪/补边**。实测产物：`ref_星海绘卷.jpg` = **1536×844**（源 1.82:1）、`ref_屏幕截图(321).jpg` = **1536×960**（源 16:10）、`ref_德丽莎2022生日.jpg` = **1536×864**（源 16:9）。16:9 由 H3 端的 `--ratio 16:9` 决定；非 16:9 素材要么在**源图上先裁/补边**，要么接受 H3 自行重构图（本歌走的是后者）。
- **低分辨率素材（≤1320×600）`81` 救不了**：`min(1536,iw)` 对 1067 宽的图就是原样。实测 `ref_月下1.jpg` = **1067×600**、`ref_月下3.jpg` = **1025×600**、`ref_10th.jpg` = **1067×600**、`ref_ElysianRealm.jpg` = **1067×600**。要让低分素材更好看，得**另做一步 2× 放大 + 降噪再喂 `81`**；本歌的实际做法是靠 §8 的本地超分在成片端补偿。
- **重复素材只用一张**：`屏幕截图(821)` 与 `(882)` 几乎同源，两张都入片会暴露同一素材。

### 4.3 素材普查的两个坑

- `plan/material_survey.md` 标题写 27 张，正文只列了 23 张；而 `01_input/CG/` 现在有 **38 个文件**。**`10th.jpg` 与 `ElysianRealm.png`（段 1 / 段 6 的参考图）不在普查表里**——下次补普查要把这两个补上，**别以为表就是全集**。

## 6. 字幕（`scripts/83_pv_subs.mjs`）

### 6.1 时间轴：行级 + 实测起音 + 实测收声 + 保底 3s

```js
next = 下一句的 t（末句 = TOTAL − 3.0）
se   = 该句的实测 sungEnd
end  = min(next, se ? max(t + 1.2, se + 0.45) : next)
end  = max(end, min(next, t + 3.0))      // 下限 3s，但绝不越过下一句
if (!(end > t)) end = t + 1.5            // 兜底
```

- 起点用 `plan/lyrics_timing.csv` 的**校正后** `use`（§1.4），不是 LRC 原值。
- **保底 3s**（`subtitle.minDisplaySec`）：换气被误判成"收声"时，字幕不会一闪而过。
- **实测收益**：`梦醒啦 别再沉湎 寻梦向前`（第 16 句）后面接 30 秒间奏，按名义时间会挂到 126.68s；用 `sungEnd = 103.32` 截断 → 止于 **103.75s**（ASS 里是 `0:01:37.00 → 0:01:43.75`，时长 6.75s）。
- 事件结束时间会 `−0.02s`（`assTime(L.end - 0.02)`），避免与下一句首尾相接时闪烁。

> ⚠️ **已知隐患**：`sungEnd` 是一个 `Map<歌词文本, 秒>` —— **重复句会互相覆盖**。本歌`哪怕有一天 泪花盛开`（第 10 与第 17 句）重复，第 10 句会拿到第 17 句的 130.64；目前被 `min(next, …)` 兜住（第 10 句止于 81.58，无可见问题）。**若重复句恰好在末尾且后接长间奏，就会取错收声时间**——改脚本时把 key 换成 `idx`。

### 6.2 多分辨率：`--tag` 不覆盖 + **必须在目标分辨率重烧**

```powershell
node scripts/83_pv_subs.mjs                                 # → subs\未来再见.ass（PlayRes 1344×768）
node scripts/83_pv_subs.mjs --w 1920 --h 1080 --tag 1080    # → subs\未来再见_1080.ass（PlayRes 1920×1080）
```

- `--tag 1080` 只改**输出文件名** + `PlayResX/Y`，**不覆盖 768 版**。
- **绝不放大会烧录过的字幕**：1080 版由 `84 --ass subs\未来再见_1080.ass` 在 1920×1080 画布上**重排重烧**，比"把 768 成片放大"锐得多。这条是 `SKILL.md` 的硬规则。
- ⚠️ **字号不随画布自动缩放**：两版 ASS 的 `Fontsize` 都是 **54**，只有 PlayRes 从 1344×768 变成 1920×1080。libass 按 PlayRes 缩放，所以 1080 版字幕的相对高度是 54/1080 ≈ **5%**、768 版是 54/768 ≈ **7%**。**要视觉等比就显式传 `--size 76`**（54 × 1080/768 ≈ 75.9）。本歌 1080 版未传。

## 7. 合成（`scripts/84_pv_assemble.mjs`）

四步，顺序不可换：

| 步 | 做法 | 关键参数 |
|---|---|---|
| 1 归一化 | 每段 → `scale=1344:768:force_original_aspect_ratio=decrease, pad=1344:768:(ow−iw)/2:(oh−ih)/2:black, fps=24, setsar=1, tpad=stop_mode=clone:stop_duration=3`；**`-an` 丢弃 H3 自带音轨**；`-t <seg.dur>` **精确裁到段长**（不足则冻末帧补足） | `libx264 -crf 16 -preset medium -pix_fmt yuv420p` → `.norm\NN.mp4` |
| 2 拼接 | concat demuxer + `-c copy` | `.norm\timeline.mp4`（**硬切直拼**） |
| 3 烧字幕 | `ass='<绝对路径>'`（`\`→`/`，`:`→`\:` 转义） | 见 §6.2 |
| 4 混音 | 用**母版** `09_aceproject/初调/翻填.wav`，`loudnorm=I=-14:TP=-1.0:LRA=11`，`-t <TOTAL>` 截齐 | `-c:v libx264 -crf 17 -c:a aac -b:a 320k -movflags +faststart` |

- **为什么必须归一化 + 精确裁**：H3 实际时长总比 `genDur` 长（§5.5），不裁整条时间轴会漂移。
- **`--timeline` 模式不会重新编码画面**：脚本里的 `W/H = 1344/768` 只在归一化分支生效；`--from-timeline` 时只过一次 `ass` 滤镜 + 混音，**1920×1080 的输入原样输出 1920×1080**。这就是"同一脚本出两个分辨率"能成立的原因。
- **为什么用硬切不用 `xfade`**：`xfade` 会缩短总时长，破坏与歌词的逐句对齐；要在转场处做溶解，必须在生成阶段多留 0.4s 余量并重算时间轴（属 v2 工作）。
- 段间 `trans` 字段（`cut` / `xfade`）目前**只用于核验报告的分类标签**，不影响拼接方式。

**三个参数与产物**（`--out` 是**相对 `10_h3video/pv/`**，不是相对工作区根）：

```powershell
node scripts/84_pv_assemble.mjs --ass 10_h3video\pv\subs\未来再见.ass `
     --out 10_h3video\pv\未来再见_PV_v2.mp4

node scripts/84_pv_assemble.mjs --from-timeline `
     --timeline 10_h3video\pv\.up\timeline_1080.mp4 `
     --ass 10_h3video\pv\subs\未来再见_1080.ass `
     --out 10_h3video\pv\未来再见_PV_v2_1080p.mp4
```

> ⚠️ **`--timeline` 必须与 `--from-timeline` 同时用**。只传 `--timeline X` 而不传 `--from-timeline` 时，脚本会**重新归一化 + 拼接并把结果写到 X**——也就是**把你指向的那个文件覆盖掉**。
> `--from-timeline` 的语义是"跳过归一化与拼接，只重做字幕与混音"，所以改字幕/改混音时可以秒级重跑。

产物（`ffprobe` 实测）：

| 文件 | 规格 | 字节 | 体积 |
|---|---|---|---|
| `10_h3video/pv/未来再见_PV_v2.mp4` | 1344×768 / 24fps / 165.875s | 94,300,548 | **94.3 MB = 89.9 MiB** |
| `10_h3video/pv/未来再见_PV_v2_1080p.mp4` | 1920×1080 / 24fps / 165.875s | 220,757,355 | **220.8 MB = 210.5 MiB（10647 kbps）** |

> **单位提醒**：`85` 的报告用 `size / 1048576` 显示，所以报告里写的"210.5 MB"其实是 **MiB**；768 版对应 **89.9**（MiB）/ **94.3**（MB）。两个数都对，**别当成不一致**。

| 超分 | ESRGAN 逐帧 PNG，**必须核验 `in`/`out` 帧数相等**，不等即 `exit 1` | — |
| 降采样 | `crop=2688:1512:0:12, scale=1920:1080:flags=lanczos`（裁掉 2688×1536 上下各 12px 得 16:9，再**超采样**） | — |
| 编码 | 每段 `libx264 -crf 14 -preset medium -pix_fmt yuv420p` | — |
| 拼接 | `parts.txt` + concat + `-c copy` | `.up\timeline_1080.mp4`，304,634,983 B = **290.5 MiB** |

**耗时：28.1 分钟**（本歌）。结束后脚本会打印下一步提示：

```powershell
node scripts/83_pv_subs.mjs --w 1920 --h 1080 --tag 1080
node scripts/84_pv_assemble.mjs --from-timeline --timeline 10_h3video\pv\.up\timeline_1080.mp4 `
     --ass 10_h3video\pv\subs\未来再见_1080.ass --out 10_h3video\pv\未来再见_PV_v2_1080p.mp4
node scripts/85_pv_verify.mjs --video 10_h3video\pv\未来再见_PV_v2_1080p.mp4 --w 1920 --h 1080
```

- **真超分 ≠ 重采样**：`lanczos`/ACE 放大只是插值像素；要真的增加细节只能用 **Real-ESRGAN** 这类模型。这条是硬纪律（`SKILL.md` §5/§6）。`lanczos` 在本链路里只用于超分**之后**的降采样。
- 超分只处理**画面**；音频在 `84` 第 4 步重新从母版混入，所以 **1080 版与 768 版音频完全一致**。
- ⚠️ **模型口径不一致**：脚本默认 `realesr-animevideov3`，而 `翻填项目.json` 的 `video.upscale.model` 写的是 `realesrgan-x4plus`。本歌实跑用的是**脚本默认值**（产物清晰度正常），但配置契约与实现对不上——下次要么把配置改成 `realesr-animevideov3`，要么显式传 `--model`。

## 9. 核验 7 项（`scripts/85_pv_verify.mjs`）

```powershell
node scripts/85_pv_verify.mjs --video 10_h3video\pv\未来再见_PV_v2.mp4 --w 1344 --h 768
node scripts/85_pv_verify.mjs --video 10_h3video\pv\未来再见_PV_v2_1080p.mp4 --w 1920 --h 1080
```

`--w/--h` **只影响第 1 项的期望分辨率**——核验 1080 版忘记带 `--w 1920 --h 1080` 就会在第 1 项误报 ❌。

| # | 项 | 阈值 | 做法 | 本歌实测 |
|---|---|---|---|---|
| 1 | 基本规格 | 时长 `165.86 ±0.05s`；分辨率 = `--w×--h`；帧率 `24/1`；视频 `h264`；音频 `aac` | `ffprobe -show_entries format=duration,size,bit_rate -show_entries stream=codec_type,codec_name,width,height,r_frame_rate -of json` | 165.875s / 1920×1080 / 24/1 / h264 / aac ✅ |
| 2 | 响度 | `I = −14 ±1 LUFS`；`TP ≤ −1 dBFS` | `ffmpeg -af ebur128=peak=true -f null NUL` | **−14.1 LUFS / −1 dBFS** ✅ |
| 3 | 指定画面抽帧 | 不判定，只存盘供**人眼复核** | `-ss <t> -frames:v 1 -q:v 2` | 48s / 68s / 86s / 134s → `verify\mandated_*.jpg` |
| 4 | 字幕 | **24 句全部出现**；字体唯一 | 读 `subs\未来再见.ass` 文本比对 + `Style: Name,Fontname` 去重 | 24/24 ✅ / 单一 `Microsoft YaHei` ✅ |
| 5 | 原创性 | **最大 SSIM < 0.90**（越低越"二创"） | `fps=1/4` 抽帧（41 帧），每帧与其**所属段**的参考图比 SSIM | **0.522**（34s vs `ref_德丽莎2022生日.jpg`）✅ |
| 6 | 接缝 | 全表记录；**链式接点 ≥0.60** | 相邻段 `clips\` 末帧（`-sseof -0.2`）vs 次段首帧（`-ss 0.05`） | 11→12 = **0.788**、12→13 = **0.885** ✅（全表见下） |
| 7 | 结论 | 任一 problem → 报告列 ❌ + `exit 1` | 汇总 | **7/7 全过** |

**第 2 项的正则陷阱**（脚本注释专门写了）：`ebur128` 的**逐帧日志里也有 `I:`**（起始静音时是 −70），**必须只取最后的汇总块**：

```js
/Integrated loudness:\s*\n\s*I:\s*(-?[\d.]+)\s*LUFS/
/True peak:\s*\n\s*Peak:\s*(-?[\d.]+)\s*dBFS/
```

**SSIM 的统一算法**（第 5、6 项共用）：两侧先 `scale=672:384`（**降到基准分辨率以下**再比），`[x][y]ssim` 取 `All:` 值。所以 768 版与 1080 版的 SSIM 结论可比，而且这个 SSIM 是**"构图级相似度"不是"像素级"**——0.522 意味着"构图相似但像素完全不同"，这正是"参考而非复制"的量化证据。
