## 1. Windows 编码四坑（**最高频，先看这节**）

### 1.1 坑 · `node -e` 内联脚本会被 PowerShell 5.1 吃掉

- **症状**：`node -e "…含引号/中文/正则的脚本…"` 报语法错、参数错位、或行为与预期完全不符；有时干脆没输出。
- **原因**：本机**只有 Windows PowerShell 5.1**。`-e` 后面的字符串要穿过 PS 的引号解析 → 原生命令行重写 → Node argv 解析三层，任何一层都能把它吃坏。
- **做法**：
  1. **一律写 `.mjs` 文件**，不用 `node -e`（项目 AGENTS.md 的硬规则）。
  2. 一次性探针脚本统一放 `dev\_probe\`，长期工具放 `tools\`，**写完保留**（它们本身就是证据）。
  3. 最小模板见 §5。

### 1.2 坑 · 用 PowerShell 读写含中文的文件 → 中文路径被写成乱码

- **症状**：文件里原本正确的中文路径，读写一轮后变成 `鏈潵鍐嶈缈诲～` 这类方块字；JSON/YAML 里的中文键值全废。
- **原因**：PS 5.1 的 `Get-Content` / `Out-File` 默认编码不是无 BOM UTF-8，往返一次就把中文写坏。
- **一手证据（本项目真实留下的）**：
  - `00_docs\00_环境与安装账本.md` §1 记着实测报错原文：`unable to locate 'E:/Videos/鏈潵鍐嶈缈诲～/...' glob`。
  - `00_docs\07_工作台能力探测报告.md` §3.2 明确记着：*"用 **Node 脚本**（不是 PowerShell）读写文件——现有文件里已有一处被 PowerShell 弄坏的中文路径，是活生生的教训。"*
  - `dev\_probe\install-fantian.mjs` 头部注释原文：*"用 Node 读写（UTF-8 干净），不走 PowerShell —— 现有文件里已有被 PS 弄坏的中文路径。"*
- **做法**：
  ```js
  // 对：Node 读写，显式 utf8
  import fs from 'node:fs'
  const p = 'C:/Users/13676/.dsh/profiles/web/cordis.patch.yml'
  const t = fs.readFileSync(p, 'utf8')
  fs.writeFileSync(p, t.replace(/\s*$/, '') + BLOCK, 'utf8')
  ```
  ```powershell
  # 万不得已必须在 PS 里写：用 .NET 显式带 BOM 的 UTF8，别用 Out-File
  [System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($true)))
  # 控制台输出对齐：脚本首行（00_env.ps1 已做）
  [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
  ```
- **现状复核（2026-09-28）**：直接读 `C:\Users\13676\.dsh\profiles\web\cordis.patch.yml`，中文路径**当前是正常的**（`name: 'file:///E:/Videos/未来再见翻填/dev/翻填工作台/index.js'`），说明那处已被修复。**但规则不变——继续用 Node 读写。**

### 1.3 坑 · `.ps1` 必须写 UTF-8 BOM

- **症状**：脚本里的中文全变乱码；或者直接 `ParserError` 起不来（中文串把语法吃坏）。
- **原因**：PS 5.1 把**无 BOM 的 UTF-8 当系统 ANSI（本机 = GBK）**读。
- **做法**：每次新增/编辑 `.ps1` 之后，跑一遍：
  ```powershell
  powershell -NoProfile -ExecutionPolicy Bypass -File E:\vsf\scripts\99_fix_bom.ps1
  ```
  `99_fix_bom.ps1` 干两件事：① 给每个缺 BOM 的 `.ps1` 补 `EF BB BF`；② 用 `[System.Management.Automation.Language.Parser]::ParseFile` **逐个解析校验**，有错的打印文件 + 行号 + 消息。
  输出形如 `Done. BOM fixed: N; files with parse errors: 0`。

### 1.4 坑 · `$ErrorActionPreference = 'Stop'` 把正常日志当致命错误

- **症状**：脚本一启动就 `NativeCommandError`，明明 Python/ffmpeg 只是往 stderr 打了条正常日志。
- **原因**：`Stop` 模式下 PS 把原生命令写 stderr 的内容当终止性错误。
- **做法**：`00_env.ps1` 刻意用 `Continue`，并提供 `Invoke-Native` 帮手——合并 stderr、原样打印、**返回退出码**，由调用方显式判断：
  ```powershell
  $code = Invoke-Native -Exe $exe -ArgList $cliArgs
  if ($code -ne 0) { throw "失败（退出码 $code）" }
  ```

### 1.5 坑 · `$Input` / `$Args` 是 PowerShell 自动变量，不能当参数名

- **症状**：传进去的输入路径变成 `E:\vsf\`（文件"丢失"），脚本报"找不到输入音频"。
- **原因**：`$Input` 会被 PS 自动清空/覆盖。
- **做法**：参数一律改名——`-InFile`（不是 `-Input`）、`-ArgList`（不是 `-Args`）。本仓库所有脚本已按此改。

## 2. ffmpeg 影子版（PATH 上的是 ImageMagick 的）

- **症状**：`ffmpeg -version` 版本不对；某些滤镜/参数报 "No such filter"；处理结果与预期不符。
- **原因**：PATH 上抢先的是 **ImageMagick 自带的 `ffmpeg.exe`**。
- **验证命令 + 期望输出**：
  ```powershell
  Get-Command ffmpeg | Select-Object -ExpandProperty Source
  # 期望（*影子版*）: C:\Program Files\ImageMagick-7.1.1-Q16-HDRI\ffmpeg.exe

  & 'E:\software\FFmpeg\ffmpeg-8.1.1-essentials_build\bin\ffmpeg.exe' -version
  # 期望（*真版*）: ffmpeg version 8.1.1-essentials_build-www.gyan.dev ...

  Test-Path 'E:\software\FFmpeg\ffmpeg-8.1.1-essentials_build\bin\ffprobe.exe'
  # 期望: True
  ```
- **做法（两层都要）**：
  1. **脚本里写全路径**：`$FFMPEG = 'E:\software\FFmpeg\ffmpeg-8.1.1-essentials_build\bin\ffmpeg.exe'`。
  2. **`.ps1` 脚本必须 dot-source `00_env.ps1`**——它把真 bin **前置**进 `$env:PATH`：`$env:PATH = "$FFMPEG_BIN;$env:PATH"`。
     这就是为什么 `10_separate.ps1` 里能直接写 `Invoke-Native -Exe 'ffmpeg'`：**它依赖 00_env.ps1 的 PATH 前置**，不 dot-source 就会用到影子版。
- **一句话纪律**：**ffmpeg / ffprobe 一律全路径**。

## 3. 中文 / 空格路径（本项目有两个根，务必看清）

| 根 | 是什么 | 谁走它 |
|---|---|---|
| `E:\Videos\未来再见翻填` | **工作区真实路径**（含中文） | 你日常打开文件、看目录 |
| `E:\vsf` | **junction → 工作区**（ASCII 别名） | **脚本 / 数据 / 命令行全走它** |
| `E:\vsf_ascii\` | **真 ASCII 目录**（不是 junction） | 给"经不起中文路径"的工具：`SXSEditor`、`DDSP-SVC`、`sxs-userdata` |

- **症状**：
  - webpack 构建失败，报 `unable to locate 'E:/Videos/鏈潵鍐嶈缈诲～/...' glob`；
  - Node/Electron 工具读到乱码路径后行为异常。
- **原因**：Python 的 `glob` / Node 的 `realpathSync.native` **在解析 junction 时会拿到中文真实路径**，随后在 GBK 代码页下变成乱码。所以走 junction **并不能**救 webpack 这类工具——它们必须待**真 ASCII 目录**里。
- **验证**：
  ```powershell
  Get-Item E:\vsf | Select-Object FullName, LinkType, Target
  # 期望: E:\vsf   Junction   {E:\Videos\未来再见翻填}
  Get-ChildItem E:\vsf_ascii -Directory | Select-Object -ExpandProperty Name
  # 期望: DDSP-SVC / singer / sxs-userdata / SXSEditor（可能另有 .bak）
  ```
- **做法**：
  1. 脚本内部**一律** `path.resolve(workspaceRoot, rel)` 拼路径；**绝不硬编码中文绝对路径**（配置规范 §0.4 的硬条款）。
  2. 配置里的路径一律**工作区相对 + POSIX 分隔符**（`/`）。
  3. 建 junction 是幂等的，重跑无害：
     ```powershell
     powershell -NoProfile -ExecutionPolicy Bypass -File E:\vsf\scripts\01_bootstrap.ps1
     # 内部: cmd /c mklink /J E:\vsf "E:\Videos\未来再见翻填"（不需要管理员）
     ```

## 4. 静默失败 & 媒体参数解析

### 4.1 每条失败路径都要打印

- **症状**：脚本"跑完了"、退出码 0，但产物不存在，你以为是别的问题。
- **原因**：失败分支只 `return` 没打日志。
- **做法**：**每条失败路径都必须打印**。本仓库的原文教训（`scripts\82_pv_clips.mjs` 注释）：
  > `log(\`段 ${s.idx} ❌ ${note}\`) // 失败必须打日志（此前静默失败过一次，别再犯）`
- **加强做法**：失败信息**落进台账**（`cost_log.csv` 的"备注"列），事后可追。

### 4.2 媒体参数一律走 `ffprobe` 的 JSON

- **症状**：时长/分辨率/帧率取到错的值（人读输出行数会变、会换行、会因版本不同而不同）。
- **做法**：
  ```powershell
  $FP = 'E:\software\FFmpeg\ffmpeg-8.1.1-essentials_build\bin\ffprobe.exe'
  $j = & $FP -v error -print_format json -show_format -show_streams $file | Out-String | ConvertFrom-Json
  $j.format.duration                                   # 秒
  ($j.streams | Where-Object codec_type -eq 'video')[0] | Select-Object width, height, r_frame_rate
  ($j.streams | Where-Object codec_type -eq 'audio')[0] | Select-Object codec_name, sample_rate, channels
  ```
- **实测样例（可直接当"长什么样"的参照）**：

  | 文件 | dur | 规格 |
  |---|---|---|
  | `02_stems\song_(Vocals)_….wav` | 163.688209s | pcm_s16le / 44100Hz / 2ch |
  | `09_aceproject\初调\翻填.wav` | 165.860000s | pcm_s16le / 44100Hz / 2ch / 27.9MB |
  | `10_h3video\pv\未来再见_PV_v2.mp4` | 165.875000s | h264 1344×768 @24fps + aac 96kHz 2ch / 89.9MB |

  响度同理用 `loudnorm … :print_format=json` 抓 JSON 块（`90_loudness_check.ps1` 就是这么做的，**不解析人读文本**）。

### 4.3 "exit 0 ≠ 产物存在"（**长作业的通用坑**）

- **症状**：ACE 的分离/转谱/导出命令返回成功，但去目录里找不到文件。
- **原因**：这些命令是 **launch 即返回 jobId** 的异步作业。官方 help 原文反复强调：*"exit 0 means the launch succeeded, not that the stems/notes/export exist."*
- **做法**：加 `--wait`（把等待折进 launch），或显式 `job wait <JOB_ID>`；多结果投递（如 stem splitter）用 `job get <JOB_ID>` 看**哪几条已经 settled**。被取消的 render 不会留半成品文件。

## 6. H3 侧三坑（视频线必撞）

### 6.1 中文 prompt 过 PowerShell 会乱码

- **做法**：中文 prompt **一律写进 `.txt`**，用 `--prompt-file` 传，**不要**走 `--prompt` 命令行参数。
- 官方 CLI 驱动：`node tools\minimax-h3\h3.mjs run --prompt-file 10_h3video\prompts\mv_test_01.txt …`

### 6.2 MCP 单次请求限 60 秒，而出片要 1–3 分钟 → **提交 → 分次轮询**

- **症状**：用 `mcp__h3__*` 一次调用等出片，等到超时失败。
- **原因**：MCP 单次请求默认超时 **60 秒**（`DEFAULT_REQUEST_TIMEOUT_MSEC`），而**实测一次 5 秒出片要 111 秒**。
- **实测时间线（照抄避雷）**：
  ```
  11:43:43  已提交任务 task_id=446283055206708
  11:43:44  状态：running
  11:45:35  状态：succeeded   （用时 111.1s）
  11:45:37  已保存 0.79 MB → 10_h3video\out\未来再见_MV测试_H3_768P_5s.mp4
  ```
- **做法**：
  - MCP 侧：`h3_generate_video` **只提交**并立刻返回 `task_id`；随后用 `h3_fetch_result` **分次轮询**（单次上限 50 秒），**不要一次调用等到底**。
  - 命令行侧：`h3.mjs run` 是一步到位（自带轮询，`--poll 10 --timeout 1800`），但**长任务建议拆成 `create` + `wait`**，避免单条命令挂太久被上层打断。

### 6.3 成片下载链接有时效；任务与素材只保留 7 天

- **症状**：过一阵再回头取成片，报 `invalid task_id`；或 URL 直接 404。
- **原因**：官方口径——**任务与上传素材只保留 7 天**；**成片下载 URL 有时效**（官方未给具体数字，V1 文件是 1 小时）。
- **做法**：**拿到就下载，别攒**。真实出片后立刻 `h3_fetch_result`（默认自动下载）或 `h3.mjs download`。

### 6.4 会直接卡住人的其余 H3 口径（全表在 `00_docs\04_*` §7）

| 症状 | 原因 / 做法 |
|---|---|
| `invalid api key` | 国内按量付费 key **只能打中国站** `https://api.minimaxi.com`（`--region cn`）；打国际站 `api.minimax.io` 必失败 |
| 报 `2013` | ① key 不是**按量付费**（Token Plan / OAuth 都不行）；② `t2va`（纯文本）**必须显式给 ratio**，且不允许 `adaptive` |
| 图生视频与参考生视频互相打架 | **互斥**：同时给 `first_frame` 和 `reference_*` 会被拒。要"参考 + 连续"→ 首镜 Ref2VA + 后续用上一段末帧续拍 |
| 状态枚举对不上 | V2 全小写 `queued/running/succeeded/failed/cancelled`；V1 是 `Preparing/Queueing/…`，**两代不通用** |
| H3-Max 参数被拒 | 档位更窄：**最短 5s、不支持 2K** |
| 解析 JSON 报错 | 服务端响应**偶尔带 BOM**，脚本已做 `\uFEFF` 剥离；自己写解析时也要剥 |
| 官方 `mmx.cmd` 出的片比预期贵 | 它**没有 `--resolution`，恒发 2K（¥0.80/s）**；且传 `--model MiniMax-H3-Max` 会错落到旧 V1 端点 → 要控档位一律走 `h3.mjs` |

## 7. ACE Studio 三坑

### 7.1 CLI 直连**正在运行**的 Studio —— Studio 没开就什么都做不了

- **症状**：所有 ACE 命令失败（连接类错误）。
- **原因**：`acestudio-cli.exe` 是 **Remote Control Bridge**，直连**正在运行的** Studio 进程，不是独立引擎。
- **做法：先探活，再动作**（每批 ACE 操作前的第一步）：
  ```powershell
  $cli = 'C:\Program Files\ACE Studio\acestudio-cli.exe'
  Test-Path $cli                                        # 期望 True（本项目已证实存在）
  & $cli project info --json                            # 任一"只读"命令能返回 JSON ⇒ 桥接可用
  & $cli editor status --json
  ```
  失败就**先让用户把 ACE Studio 打开**，别去猜参数。
- **第二条纪律**：**CLI 与 MCP 两条路线驱动同一个 Studio，不要同时用。** CLI 能用时不必注册 MCP。

### 7.2 语法一律查 `help`，不要凭记忆猜

```powershell
& $cli help                                   # 命令总表 + 主题列表
& $cli help convert tick-to-time              # 单个命令
& $cli help tick-coordinates                  # 主题文档（tick 规则就在这里）
& $cli help --search 'stem|split'             # 全库正则搜索
```
- **实测（2026-09-28）：`help` 是**离线可用**的**——Studio 不必在跑，`help` 依然返回完整命令表与主题文档。查语法不需要先开 Studio。
- 官方技能是"know-how 层"（什么时候用哪个），CLI `help` 是"语法层"。**做 ACE 的活之前先加载 `ace-studio-features` / `ace-studio-workflows`。**

### 7.3 长作业与会话工程

- 三类长作业（`generative stem-splitter` / `generative vocal-to-midi` / `export audio`）都是 **launch 返回 jobId**，见 §4.3。
- ACE 的**导入类**操作是**原子的**：`import file` 被拒时**不留残留轨道**。
- 项目文件（`.acep`）是**用户的东西**：`09_aceproject\` 是**只读保护区**，不删不改；要备份就复制到 `07_mix\ACE_*`（本项目已这么做）。

## 9. 本次开发新踩的坑（技能 / 预设 / 插件侧）

### 9.1 技能 `name` 必须匹配 `/^[a-z0-9]+(?:-[a-z0-9]+)*$/` → **不能用中文当技能名**

- **源码证据**：`…\@deepseek-ai\dsh\node_modules\@deepseek-ai\dsh-skill\lib\index.js`
  - **L17**：`const SKILL_NAME = /^[a-z0-9]+(?:-[a-z0-9]+)*$/;`
  - L454 / L466 / L481：三处校验，不匹配直接抛 `invalid skill name` / `loaded skill has invalid name`
- **失败表现**：**整个技能被静默跳过**。发现链路是 `skill-filesystem` 的 `discoverRoot()` → `parseSkillFile()` 解析失败返回 `undefined` → `continue` —— 你不会看到报错，只会看到"技能列表里没有它"。
- **做法**：
  - frontmatter 的 `name` 用**纯小写 ASCII + 连字符**：本技能 = **`fanfill-video-pipeline`**。
  - **目录名无所谓**（技能名取自 frontmatter），但**目录与 name 保持一致更可维护**。
  - 中文名保留在 `description` 与正文里，**触发效果不受影响**（触发看 description）。

### 9.2 技能根只认**一层深** `<root>\<名字>\SKILL.md`

- **源码证据**：`dsh-skill-filesystem\lib\index.js`
  - 扫描用 `depth: 1`；
  - 潜在技能路径判定：`segments.length === 2 && segments[1] === 'SKILL.md'`；
  - 发现逻辑：对根下每个目录 `join(entry.path, 'SKILL.md')` 去找。
- **推论**：`<root>\<名字>\references\01_x.md`、`<root>\<名字>\scripts\*.mjs` **都行**（子目录随便放）；但 `<root>\a\b\SKILL.md`、`**/SKILL.md` 这种**嵌套不认**。
- 根目录被 **Chokidar 监视** → **装进去立刻生效，无需重启**。

### 9.6 Client 插件（`dsh.client`）的解析基准 = **它自己 `package.json` 的同目录祖先**

- **机制**：`dsh-client-modules` 的 `locatePkgJson(loaderName, baseUrl)`（`lib/index.js` **L743–773**）对以 `file:` / `.` / 绝对路径开头的 loader 行，走 `nearestPackage(moduleUrl)`——**从该文件所在目录向上找最近的 `package.json`**，再读它的 `dsh.client` 与 `exports["./client"]`。
- **推论（这是本次的关键发现）**：profile 补丁行只要写**绝对路径**，Client 半边就会被自动发现，**不需要**把包名塞进 profile 的 `package.json` 依赖里：
  ```yaml
  - insert:
      - id: fantian-workbench
        name: 'file:///E:/Videos/未来再见翻填/dev/翻填工作台/index.js'
        config:
          workspace: 'E:/Videos/未来再见翻填'
  ```
- **前提**：`<bundle 目录>\package.json` 里必须有
  ```json
  "dsh": { "client": { "platform": "web", "immediately": true, "inject": [ ... ] } },
  "exports": { "./client": "./client.js" }
  ```
- Host 半边按普通 ESM 解析 → `file:///` URL 直接可用（已实测 `import` 成功）。

### 9.7 客户端插件改动的热更条件 & 验证局限

- 客户端改动**要在同一个 checkout 跑 `pnpm run dev:web`** 才会热重载；否则**改完必须刷新页面**。改其它（Web shell / 普通包）**一律要重新构建 + 刷新**。
- **不要**先做 HTML 预览稿——用**已安装的插件本身**当预览。
- **验证局限必须明说**（`07_工作台能力探测报告.md` §6 原文口径）：本项目**没有浏览器控制**，Host 半边在真实数据上返回正确快照、`node --check` 通过、Client 解析路径在源码层面成立——但 **"用户一定看得见面板"当时尚未被证实**，需要重启 `dsh web` 后由用户实际打开确认。**没有证据就不要说已验证。**
